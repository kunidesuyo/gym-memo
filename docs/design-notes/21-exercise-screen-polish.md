# 21. 種目画面のブラッシュアップ —— 2026-09-21

### 変更

| | 変更前 | 変更後 |
|---|---|---|
| `/exercises` | 一覧 + 編集・削除ボタン + インライン追加フォーム | **一覧と絞り込みだけ** |
| `/exercises/$id` | 記録の履歴のみ | 履歴 + **この種目の編集・削除** |

**役割分担の意図**: 一覧は「探す」ための画面、詳細は「その種目を扱う」ための画面。
一覧に操作ボタンを並べると、行が窮屈になり誤タップも増える（スマホで片手で使う前提）。

### 絞り込みはクライアント側で行う

分割(PPL)と部位のチェックボックス。**チェックした瞬間に反映**される。

```
絞り込み                      [クリア]
分割  [ ] Push  [x] Pull  [ ] Legs
部位  [ ] 胸 [ ] 肩 [ ] 三頭 [x] 背中 ...
```

**サーバーに問い合わせない理由**: 種目は十数件しかない。API には `?category=push` があるが、
- 複数選択のたびにリクエストが飛ぶ
- 組み合わせごとにキャッシュキーが増える
- ローディング状態が挟まって「すぐ反映」にならない

→ **手元で `filter()` するのが速く、状態も単純**。件数が3桁になったら考え直す。

絞り込みの意味: **同じ軸の複数チェックは OR、軸をまたぐと AND、何も選ばなければ全件。**

**クリアボタンは常時表示**（選択の有無で出し入れしない）。ボタンが現れたり消えたりすると
レイアウトが動いて押し間違える。

### 見つけたバグ: `isError` をクロージャから読んでいた

削除のテストを書いたら**実コードのバグが出た。**

```tsx
// ❌ 壊れている
await remove.mutateAsync(id).catch(() => {})
if (!remove.isError) navigate({ to: '/exercises' })
```

`remove.isError` は**そのレンダー時点の値**。`await` の後もクロージャは古い値（false）を
掴んだままなので、**削除が 409 で失敗しても画面遷移してしまう**。

```tsx
// ✅ Promise の結果で判断する
try {
  await remove.mutateAsync(id)
  navigate({ to: '/exercises' })
} catch {
  // 理由は remove.error として表示する
}
```

**同じバグが `WorkoutDetail` のセッション削除にもあった**（1-e で書いたもの）。
そちらも修正し、回帰テストを追加した。成功時しか試していなかったので気づけていなかった。

→ **教訓: 削除・更新は失敗系こそテストする。**
