# 28. メインセット / 移行データの誤読3件（2026-09-23）

ウォームアップと本番セットを分けて伸びを追いたい。`sets.is_main_set` を足す。

### 判定規則 —— 実データで測ってから決めた

移行済みの4,194セット・989グループ（日付×種目）を解析した。

```
グループのセット数   3以下 467 (47%) / 4-5 256 / 6-7 243 / 8以上 23
```

**ラスト3セット**を本番とみなす仮説を4セット以上の522グループで検証:

| | 件数 |
|---|---|
| ラスト3より重いセットが手前にある（戻し・ドロップで終わる日） | 13グループ (2%) |
| ラスト3がまだ増量中（アップを巻き込む） | 18グループ (3%) |

95%以上は狙い通り。ユーザー判断で**重量による補正はかけない**
（「メインセット内で重量が変わることはあり得る」）。

ただしラスト3だけだと **1RM 測定日**を取りこぼす。あの日はウォームアップの奥から
シングルの階段が続くため、本番が4本以上ある。

```
2025-10-01 デッドリフト  20×10 60×8 [100×1 120×1 130×1 140×1 145×1 150✗ 147.5✗]
                                     ↑ここから全部が max 挑戦
```

**採用: (日付, 種目) ごとのラスト3セット ∪ reps≤1 のセット**。
失敗（reps 0）も max 挑戦なので含める。ラスト3のみとの差は10グループ・21セットで、
その10グループが全部 1RM 測定日だった。

#### 懸垂だけは回数で判る（後から追加）

懸垂の回数は **5回と10回しかない**。10回でアシストを減らしていき、本番は5回。
本番が6本続く日があり、ラスト3では前半3本を取りこぼしていた。

```
2026-08-23  -18×10 -18×10 [-14×5] [-14×5] [-9×5] [-9×5] [-9×5] [-9×5]
                          └───────────── ここから全部が本番 ─────────────┘
```

⚠️ 逆向き（10回は常にアップ）は**成り立たない**。130日のうち125日は10回しかやっておらず、
その日は10回が本番。**「懸垂で5回なら本番」という向きだけ**を足す。

**規則: ラスト3 ∪ reps≤1 ∪ (懸垂 かつ reps≤5)**。

#### 残りは1グループずつ手で決めた

規則で埋めたあと全989グループを監査し、怪しいものを2種類あぶり出した。

| | 件数 | 症状 |
|---|---|---|
| B | 18 | 3セット以下なので全部メインになったが、実際は重量の階段だった |
| C | 9 | 戻し・ドロップで終わる日。ラスト3だとピークがアップ扱いになる |

重量による自動補正も試したが**使えなかった**。懸垂のアシスト量が負数なので
「後により重いセットがあるか」の比較が壊れ、同じ重量の3セットまで降格する。

```
前  2024-09-30 懸垂  [-36×10] [-36×10] [-36×10]
後  2024-09-30 懸垂   -36×10   -36×10  [-36×10]   ← 誤り
```

→ 27グループを**1つずつユーザーに確認**し、`main-set-overrides.ts` に列挙した。
うち22件が変更、5件が「規則どおりでよい」。
判定ロジック（`main-sets.ts`）と手動指定を別ファイルに分けてあるのは、
前者がアルゴリズム、後者が**ユーザーの判断の記録**で、寿命が違うため。

**最終: 2,900 / 4,190 (69%)**

⚠️ 手動指定はセット番号（1始まり）で持っている。`CELL_FIXES` を変えると番号がずれる。

バックフィルは `0002` の末尾に手書きで置いた（drizzle-kit は DML を生成しない）。
インポートスクリプトも同じ規則で `is_main_set` を吐くので、**再インポートしても再現する**。

### 画面

- 記録フォームに「メインセット」チェックボックス。**既定オフ**。
  メインかどうかはセッション終盤にならないと決まらないので、自動判定はしない
- 連続入力で `isMainSet` は**リセットしない**（本番は続けて何本か組むため）
- セッション詳細では**メインはそのまま、アップを `text-muted-foreground` に落とす**。
  バッジを足すより本番だけが浮き上がるほうがスマホ幅で読みやすい
- 編集は `SetForm` を使い回しているので、トグルは自動で付いてくる

⚠️ ついでに直したバグ: 「失敗」チェックボックスが**反転していた**。
`isSuccessful`（既定 true）の値を「失敗」というラベルで出していたため、
成功しているのにチェックが入って見えていた。ラベルを値と同じ向きに直した
（当初は「挙がった」。2026-09-23 に「成功」へ変更）。
**boolean のラベルは値と同じ向きにすること。**

### 移行データの誤読3件

解析の副産物として、幽霊セット15件と種目の取り違えが見つかった。全てユーザー確認済み。

| 元セル | 症状 | 原因 | 影響 |
|---|---|---|---|
| `デクライン3 腹筋10×3` | アブローラーに **3kg×1回** が生える | `splitToken` が「テキスト＋数値」の数値を重量として拾っていた。`3` は腹筋台の段数 | 11日 |
| `腹筋　デクライン4:10 3:10×2` | 腹筋に **10kg×1回** が生え、**3セット目が消える** | 同上。`4:10` の `10` は回数 | 2日 |
| `デクライン2腹筋10×3` | 腹筋のセットが**アブローラー**として記録される | スペースが無く `腹筋` を種目名として切り出せない | 3日(9セット) |
| `パラレルmag 39×10 45×10⏎-18×10 -14×10` | 懸垂2セットが**ラットプルダウンに混ざる** | 改行を潰していたので種目の乗り換えが行をまたいだ | 1日 |

直し方:

1. **`splitToken`**: テキストに続く素の数値は仕様として拾わない。
   例外は `4:` のように **`:` で終わる**前置きのときだけ（設定値の書式）
2. **`parseSpec`**: 自重種目（腹筋・アブローラー）の素の数値は**回数**として読む。
   自重に重量は書かれない
3. **セルの走査を「行」単位に**。改行は別ブロックで、種目の乗り換えは行をまたがない
   （改行を含むセルはCSV全体で1つだけだった）
4. 設定メモ（デクラインの段数、マシン番号）は**積み上げず上書き**する。
   `デクライン4:10 デクライン3:10×2` を繋ぐと「デクライン4 / デクライン3」になってしまう。
   グリップ指定（`パ`）は逆に**そのトークンだけ**——`パ-18×10 -18×10` の2本目は
   パラレルグリップではない
5. 曖昧な2セルは `CELL_FIXES` でラベルを補って明示

結果 4,194 → **4,183セット**（幽霊15件を削除、消えていた実セット2件を復元、
種目の付け替え11セット）。旧データとの差分を全件突き合わせ、
**意図した変更以外はゼロ**であることを確認した。

#### 黙って捨てられていたトークン（後から発見）

メインセットの確認中に、**数値仕様として読めず例外も出さずに読み飛ばされていた**
トークンが3つ見つかった。全セルを走査して洗い出した3件で打ち止め。

| 元セル | 落ちていたもの |
|---|---|
| `20×10 40×10 50×` | `50×` は `50×10` の打ち間違い（回数欠落＝失敗ではなかった） |
| `20×10 40×10 60×5×.3` | `×.3` は `×3`。60kg×5 が **3セット** |
| `(4) 38×10 41×10×2)` | 末尾の `)` が余分。41kg×10 が **2セット**（2日分） |

⚠️ **パーサは読めないトークンを黙って捨てる。** これが一番こわい壊れ方だった
（セットが消えても件数以外に痕跡が残らない）。
`parseSpec` が空配列を返すトークンを全件走査する形で検出した。
`CELL_FIXES` で修正し、4,183 → **4,190セット**（失敗も11→10件に）。

⚠️ 副次的に `note` が「デクライン」→「デクライン3」のように段数まで残るようになった
（末尾のコロンも落として表記を統一）。
