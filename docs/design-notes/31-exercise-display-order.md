# 31. 種目の並びを手動指定にする（2026-09-28）

### きっかけ: 種目一覧が意外に重かった

インフラ費用を見積もる過程で `GET /api/exercises` の実測を取った。

```
4,401 行読んで 51 行返す（21.6ms）
```

「セット数の多い順」に並べるために `sets` を全件 join して数えていた。
無料枠（5,000,000 行/日）からすれば 1,136 回/日まで叩ける計算で**実害は無い**が、
`new QueryClient()` の既定値（`staleTime: 0` / `refetchOnWindowFocus: true`）と
組み合わさるので、スマホで別アプリから戻るたびに走っていた。

`staleTime` を足す小細工も検討したが、**並びを手動指定にすれば join ごと消える**
ことに気づいたので、そちらを採った。

### 決めたこと

| 論点 | 決定 |
|---|---|
| スコープ | **分割の中**での順番。全51件の通し番号は管理が重い |
| 列名 | **`display_order`**。`sort_order` は既存の `sets.set_order` と紛らわしい |
| UNIQUE | **張らない** |
| 既定値 | **999 = 未設定**。番号を振った種目より下に沈む |
| 並び | `分割（Push→Pull→Legs→その他） → display_order → 名前` |
| `setCount` | **API から削除**。どの画面も読んでいなかった |

### なぜ複合 UNIQUE を張らないか

当初 `UNIQUE(category, display_order)` の案が出たが、3つの理由で却下した。

1. **入れ替えができない。** A(1) と B(2) を交換するとき、A を 2 にした瞬間に衝突する。
   SQLite は文ごとに制約を見るので、一時値を経由するか全件振り直す必要がある
2. **分割の変更が 409 になる。** push(3) の種目を pull に移したとき、pull に 3 が
   あると弾かれる。ユーザーには「部位を変えただけなのに」としか見えない
3. **「気にしない種目」を放置できない。** pull は27件あるが、実際に順番を決めたいのは
   上位数件だけ

同値は名前順で解決するので、**重複を許しても並びは決定的**。

### なぜ既定値が 0 ではなく 999 か

**テストを書いていて気づいた。** 既定 0 だと、番号を振っていない種目が
**一番上に来る**。「よく使う種目に 1〜10 を振って、残りは放置」という運用と逆になる。

999 にすると未設定は分割の末尾に沈み、番号を振ったものが上がってくる。
新しく作った種目も 999 なので末尾に入る（試している段階の種目が
いきなり選択肢の先頭に来ない）。

⚠️ DB のデフォルト・Zod の `.default()`・フォームの空欄変換の**3箇所**を
999 に揃えてある。1つでも 0 のままだと経路によって挙動が変わる。

### 記録画面を分割で絞る

```
[すべて] [Push] [Pull] [Legs]
種目     [ベンチプレス ▾]
```

⚠️ **その他（腹筋・アブローラー）はどの分割を選んでも末尾に出す。**
腹筋系はどの日にもやるため。サーバーが分割順に並べているので、
クライアントは絞るだけでその他が末尾に残る（並べ替え不要）。

⚠️ 絞り込みは**クライアント側**（21章の規約どおり、ボタンを押しても API は叩かない）。
51件を最初に1回取るだけで、切り替えは完全にオフライン。

⚠️ 絞り込みで選択中の種目が消えたら**選択も外す**。残すと `<select>` の value に
合う option が無くなり、空欄に見える。

分割選択の UI はネイティブ `<select>` ではなくボタン列にした。20章の
「ネイティブ `<select>` を使う」は**50件の種目**に対する判断で、4件なら
1タップで切り替わるボタンのほうが速い。

### 踏んだもの

#### 手書きマイグレーションのスナップショットが連鎖を壊していた

28章で `0003_pullup_main_sets.sql`（DML のみ）を手で足したとき、
`0002_snapshot.json` をコピーしただけで `id` / `prevId` を直していなかった。

```
Error: [migrations/meta/0002_snapshot.json, migrations/meta/0003_snapshot.json]
are pointing to a parent snapshot ... which is a collision.
```

`db:generate` が通らなくなって初めて発覚した。
⚠️ **DML だけのマイグレーションを手で足すときは、スナップショットの
`id` を新しい UUID に、`prevId` を直前のものにすること。**

#### ローカルでは移行 DML が空振りする

`db:reset:local` は「空の DB にマイグレーション → そのあと import」の順なので、
既存行を更新する DML は何も更新しない。本番は既にデータがあるので正しく効く。
ローカルで移行結果を確認したいときは、同じ UPDATE を手で流す。

#### デプロイ中に wrangler の OAuth トークンが切れた

`db:migrate:remote` が「権限一覧を吐いて exit 1」という紛らわしい落ち方をし、
再実行すると `✅ No migrations to apply!` と出た。直後から D1 への全クエリが
`Authentication error [code: 10000]`。

**適用されたのかどうかログからは判断できなかった。**
`wrangler login` をやり直し、`d1_migrations` テーブルを直接見て確定させた
（1回目で適用されていた）。

⚠️ **「エラーが出た後の成功メッセージ」を信用しないこと。**
マイグレーションの適用有無は `d1_migrations` を見る。
